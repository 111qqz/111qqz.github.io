起因
#

最近在做 CS336（Language Modeling from Scratch）的 resource accounting 作业，里面要求逐个列出 Transformer forward pass 中所有的 matmul，然后按 \(2MKN\) 计算 FLOPs。

算完之后自然会想：算出来的 FLOPs 到底能在多大程度上代表真实的推理性能？

这个问题不只是学术好奇。实际工作中遇到过一个模型调度问题：需要把多个模型分配到一组 GPU 上，希望让最慢模型的 inference latency 尽可能小。

最直觉的想法是：用模型 FLOPs 来表示它需要多少 GPU 算力，然后按 FLOPs 做分配。

但实际 profiling 很快发现：即使两个模型的理论 FLOPs 很接近，不同的 GEMM shape 也可能导致非常不同的 inference latency。

对 MoE、GNN 这类模型，这个问题更加明显。

这篇笔记就是从这个观察出发，试图把 FLOPs 和 latency 之间的关系讲清楚。

核心结论先放在这里：

FLOPs 是 workload metric，不是 performance metric。

FLOPs 回答的是"数学上需要做多少浮点运算"，而 latency 回答的是"这些运算在具体 GPU 上要跑多久"。二者中间隔着一个非常重要的层次：Hardware Efficiency。

一个看似合理的公式
#

假设模型做一次 forward 需要 \(F\) FLOPs，GPU 的 peak compute capability 是 \(P\) FLOP/s，那么最容易想到的估算是：

$$T = \frac{F}{P}$$

比如模型 10 GFLOPs，GPU peak 100 TFLOPS，那理论时间就是 \(10G / 100T = 0.1\) ms。

这个计算有什么价值？它给出了一个非常粗略的 theoretical lower bound。

但实际 latency 往往远大于它。

于是问题变成：为什么 GPU 明明有 100 TFLOPS，却经常只能跑出其中很小一部分？

这里需要引入一个概念：

$$\text{Achieved FLOPS} = \frac{\text{Actual FLOPs}}{\text{Execution Time}}$$

也就是 GPU 在执行这个 workload 时，实际达到的每秒浮点运算数。

真正应该使用的关系是：

$$\text{Latency} = \frac{\text{FLOPs}}{\text{Achieved FLOPS}}$$

问题从"怎么算 FLOPs"变成了"什么决定 Achieved FLOPS"。

整篇文章后面都在回答这个问题。

FLOPs 统一口径
#

在展开之前，先把 FLOPs 的计算口径统一一下。

对于 GEMM（通用矩阵乘法）：

$$C = AB$$

其中 \(A \in \mathbb{R}^{M \times K}\)，\(B \in \mathbb{R}^{K \times N}\)，\(C \in \mathbb{R}^{M \times N}\)。

每个输出元素需要 \(K\) 次 multiply 和 \(K\) 次 add，因此：

$$\text{FLOPs}_{\text{GEMM}} = 2MKN$$

本文的口径是：multiply = 1 FLOP，add = 1 FLOP，一个 MAC（multiply-accumulate）= 2 FLOPs。

需要注意的是，有些 profiler 和论文把一个 MAC 当作 1 operation，所以可能存在 2x 的统计差异。CS336 的作业用的也是 \(2MKN\) 的口径。

这里真正重要的一点是：\(2MKN\) 只取决于三个维度的乘积。

从纯数学工作量来看，只要 \(M_1 K_1 N_1 \approx M_2 K_2 N_2\)，两个 GEMM 的 FLOPs 就几乎相同。

那么问题来了：为什么实际 latency 可能完全不同？

Same FLOPs, Different Latency
#

这是整篇文章的核心观察。

假设我们构造几组 GEMM，控制 \(2MKN\) 的乘积相同，但 shape 明显不同：

ShapeMKNFLOPs
balanced204820482560~21.5G
medium-skinny32409681920~21.5G
tall-skinny140962621440~21.5G

FLOPs 几乎一样。但如果在 GPU 上实际跑一下（用 torch.matmul + CUDA Event 计时），会发现：

  • balanced shape 的 Achieved TFLOPS 可能接近 GPU peak 的 70-80%
  • skinny shape（尤其 M=1）的 Achieved TFLOPS 可能只有 peak 的个位数百分比

也就是说：

$$\text{FLOPs}_A \approx \text{FLOPs}_B$$

但是：

$$\text{Achieved FLOPS}_A \gg \text{Achieved FLOPS}_B$$

因此：

$$\text{Latency}_A \ll \text{Latency}_B$$

这就是整篇文章要解释的事情：这些 FLOPs 到底是怎么被 GPU 执行的？

GEMM Shape 与 GPU Parallelism
#

先说第一个原因：GPU 需要足够的并行度。

GPU 是一台有几千个工人的工厂
#

GPU 有大量的 SM（Streaming Multiprocessor），每个 SM 里有很多 warp，还有 Tensor Core。

FLOPs 告诉你一共有多少工作。但如果这些工作无法同时拆给很多工人，那工人数量再多也没用。

Peak FLOPS 只是硬件在"工作足够适合并行"的情况下能够达到的上限。

GEMM 的 tiled execution
#

GPU 执行 GEMM 不是真的逐个算 \(C_{ij} = \sum_k A_{ik} B_{kj}\)。

实际的 GEMM kernel 会把输出矩阵 \(C\) 按 block/tile 切分，每个 tile 映射到一个 thread block，tile 内部再拆到 warp 和 Tensor Core instruction。

 1Output Matrix C
 2┌──────┬──────┬──────┬──────┐
 3│ tile │ tile │ tile │ tile │  ← 每个 tile 映射到一个 thread block
 4├──────┼──────┼──────┼──────┤
 5│ tile │ tile │ tile │ tile │
 6├──────┼──────┼──────┼──────┤
 7│ tile │ tile │ tile │ tile │
 8└──────┴──────┴──────┴──────┘
 9
10M 和 N 决定输出矩阵的大小
11→ 决定 tile 的数量
12→ 决定能同时启动多少个 thread block
13→ 决定 SM 能不能被填满

因此 \(M\)、\(K\)、\(N\) 不仅决定 FLOPs，还决定了 tile 数量、tile 是否完整、edge tile 有多少、warp utilization、occupancy 等等。

\(MKN\) 相同，不意味着硬件执行效率相同。

Skinny GEMM 为什么尤其低效
#

当 \(M\) 非常小的时候（比如 \(M=1\)，对应单 sample inference），输出矩阵变成 \([1, N]\)，tile 数量急剧减少。

具体来说：

  • available parallelism 下降： 只有很少的 tile，无法把所有 SM 填满。大量 SM 空闲。
  • data reuse 模式改变： 大 GEMM 中，A 矩阵的一个元素会被多个输出行复用；M=1 时这种复用消失了。
  • fixed overhead 占比增加： kernel launch、synchronization 这些固定开销，在总计算量很小时占比变大。

这对低 batch inference 非常重要——online serving 的 batch size 经常是 1 或者个位数。

Shape alignment
#

不同的 GPU architecture、dtype、CUDA/cuBLAS/CUTLASS kernel 对 tile shape 有不同偏好。某些维度如果能较好地匹配 Tensor Core instruction 或 vectorized memory operation，效率会更好。

实践中 1024、2048、4096 这类维度比较常见。

但这里要加一个 caveat：不存在一个所有 GPU、dtype、kernel 都通用的"必须是 8/16/32 的倍数"规则。 不要过度简化。

Arithmetic Intensity
#

除了 parallelism 和 tiling，还有另一个关键因素：数据搬运。

即使计算单元有足够的并行度，GPU 还需要把数据从显存搬到计算单元。如果搬数据的速度跟不上计算速度，计算单元就只能等着。

这里需要引入一个核心概念：

$$\text{Arithmetic Intensity} = \frac{\text{FLOPs}}{\text{Bytes Transferred}}$$

单位是 FLOPs/Byte。它回答的是：GPU 每从 memory 搬运 1 byte 数据，可以完成多少次计算？

直觉
#

High AI（高算术强度）：

1从 HBM load 一块数据
2     ↓
3放入 shared memory / register
4     ↓
5反复 reuse，执行很多 multiply-add
6     ↓
71 byte 数据支撑很多 FLOPs

计算很多，搬数据相对少。GPU 的计算单元能一直保持忙碌。

Low AI（低算术强度）：

1从 HBM load 数据
2     ↓
3做一两次操作
4     ↓
5结果写回 HBM
6     ↓
7继续 load 新数据

GPU 算得再快也没用，因为大多数时间都在等数据。

Bytes 是 memory traffic，不是 tensor size
#

这里有个容易搞混的地方。Arithmetic Intensity 中的 Bytes Transferred 不是简单的 input tensor size + weight size + output size。

它关心的是实际的 memory traffic——数据在 memory hierarchy 中来回搬运的总量。

实际 traffic 受 cache、tiling、data reuse、kernel fusion、hardware cache hierarchy 等因素影响。分析时经常用 theoretical arithmetic intensity 作为近似，但真正 profiling 时可以用 Nsight Compute 等工具来测。

为什么 GEMM 通常具有较高 Arithmetic Intensity
#

矩阵乘法天然具有很好的 data reuse。

\(A\) 的某个元素 \(A_{ik}\) 会参与 \(C\) 的第 \(i\) 行所有 \(N\) 个元素的计算；\(B\) 的某个元素 \(B_{kj}\) 会参与 \(C\) 的第 \(j\) 列所有 \(M\) 个元素的计算。

通过 tiling，kernel 可以把一小块 A 和 B load 到 shared memory / register，然后反复用这些数据做大量 FMA（fused multiply-add）。

1HBM
2 ↓ load tile
3Shared Memory / Registers
4 ↓ reuse
5大量 FMA 操作

这就是 GPU 极其擅长大矩阵乘法的核心原因之一：有限的 memory traffic 可以支撑大量 FLOPs。

GEMM 的 Arithmetic Intensity 推导
#

假设 \(A: M \times K\)，\(B: K \times N\)，\(C: M \times N\)，每个元素占 \(s\) bytes。

最理想的最低数据搬运量可以粗略写成：

$$\text{Bytes} \approx s(MK + KN + MN)$$

FLOPs 是 \(2MKN\)，于是：

$$\text{AI}_{\text{GEMM}} \approx \frac{2MKN}{s(MK + KN + MN)}$$

这是理论估算，不代表真实 HBM traffic。但它特别适合帮助理解 shape 的影响。

比如当 \(M\) 非常小的时候，分母中 \(KN\) 项会占主导（weight 矩阵很大但只用一次），AI 就会下降。

也就是说：batch size / GEMM shape 不只是改变 FLOPs，也会改变 Arithmetic Intensity，从而改变硬件效率。

Roofline Model
#

有了 Arithmetic Intensity 的概念，就可以引入一个非常有用的分析框架：Roofline Model。

核心公式：

$$\text{Achievable FLOPS} \le \min(\text{Peak FLOPS},\ \text{Memory Bandwidth} \times \text{AI})$$

用图来表示：

 1Achieved FLOPS (log)
 2     ^
 3     |
 4     |                         ─────────── Peak Compute
 5     |                       /
 6     |                     /
 7     |                   /   ← slope = Memory Bandwidth
 8     |                 /
 9     |               /
10     |             /
11     |___________/________________________> Arithmetic Intensity (log)
12          Memory-bound        Compute-bound

横轴是 Arithmetic Intensity（建议 log scale），纵轴是 Performance（FLOP/s）。

两部分：

  • 斜线部分： \(\text{Performance} = \text{BW} \times \text{AI}\)，workload 受 memory bandwidth 限制
  • 水平线部分： \(\text{Performance} = \text{Peak FLOPS}\)，workload 受 compute 限制

两者的交点叫 ridge point：

$$\text{AI}_{\text{ridge}} = \frac{\text{Peak FLOPS}}{\text{Memory Bandwidth}}$$

workload 的 AI 必须高于这个值，才有机会进入 compute-bound 区域。

用数字来感受
#

假设 GPU peak = 100 TFLOPS，HBM bandwidth = 2 TB/s。

$$\text{AI}_{\text{ridge}} = \frac{100}{2} = 50\ \text{FLOPs/Byte}$$

Workload A： AI = 5 FLOPs/Byte

$$\text{Performance} \le 2\ \text{TB/s} \times 5 = 10\ \text{TFLOPS}$$

虽然 GPU 名义上 100 TFLOPS，但这个 workload 理论上最多只能获得 10 TFLOPS。

Workload B： AI = 100 FLOPs/Byte

bandwidth roof = 200 TFLOPS，已经超过 compute peak 100 TFLOPS，所以受 compute roof 限制。

Peak TFLOPS 是硬件属性；真正能使用多少，要看 workload 落在 Roofline 的什么位置。

Roofline 的局限
#

Roofline 是一个非常有用的 mental model，但它不是 latency predictor。

它给的是 upper bound。

比如两个 GEMM，Arithmetic Intensity 都很高，按 Roofline 都在 compute-bound 区域——但如果一个 M=4096，另一个 M=4，实际 Achieved FLOPS 仍然可能差很多。

为什么？因为 Roofline 没有描述：

  • insufficient parallelism（tile 数量不足）
  • occupancy
  • tile efficiency
  • instruction utilization
  • launch overhead
  • synchronization
  • load imbalance

所以：Roofline 是必要的 mental model，但不是完整的 GPU performance model。

三层 Mental Model
#

到这里可以把全文最核心的认知框架画出来：

 1              Model / Workload
 2                     │
 3                     ▼
 4             Theoretical FLOPs         ← 数学上有多少工作？
 5                     │
 6                     ▼
 7       ┌──────────────────────────┐
 8       │    Execution Properties  │
 9       │                          │
10       │  GEMM Shape              │
11       │  Parallelism             │
12       │  Arithmetic Intensity    │
13       │  Memory Access Pattern   │
14       │  Kernel Implementation   │
15       └─────────────┬────────────┘
16                     │
17                     ▼
18              Achieved FLOPS           ← 硬件每秒能完成多少？
19                     │
20                     ▼
21                Latency                ← 最终性能

从 FLOPs 到 Latency 不是一步到位的。中间那一层 Execution Properties 决定了 Achieved FLOPS，而 Achieved FLOPS 才是连接 FLOPs 和 Latency 的桥梁。

$$\text{Latency} = \frac{\text{FLOPs}}{\text{Achieved FLOPS}} = \frac{\text{Work}}{\text{Efficiency}}$$

FLOPs 描述 Work，Achieved FLOPS 描述 Efficiency，Latency 才是 Performance。

不要把 FLOPs → Latency 的关系简化成一步。

MLP：FLOPs 比较有效的 baseline
#

前面一直在说 FLOPs 不能直接预测 latency。但也不要把它批判成"完全没用"。

对一个以 large dense GEMM 为主、shape 比较稳定的模型，FLOPs 确实是一个相当好的 first-order performance metric。

比如一个两层 MLP：

$$[B, D] \times [D, H] \rightarrow [B, H] \times [H, D]$$

FLOPs 约 \(4BDH\)。

如果两个 MLP 的 \(B\)、\(D\)、\(H\) 相似，dtype 相同，跑在同一张 GPU 上，GEMM shape 都比较 healthy（M 不太小、维度对齐良好），那么：

$$\text{FLOPs}_A > \text{FLOPs}_B \implies \text{Latency}_A > \text{Latency}_B$$

大概率是成立的。

FLOPs 是一个很好的 first-order metric，只是需要知道它的适用条件。

Batch Size：FLOPs 线性增长，Latency 不按比例增长
#

用同一个 MLP 来看 batch size 的影响。

GEMM shape 是 \([B, D] \times [D, H]\)，FLOPs 与 \(B\) 成正比。

从 B=1 到 B=128，FLOPs 增加 128 倍。

但 latency 很可能不会增加 128 倍。

因为 B=1 时 GEMM 非常 skinny，GPU 利用率很低；B=128 时 GEMM 变大，GPU 可以被充分利用。

$$\text{Achieved FLOPS}(B=128) \gg \text{Achieved FLOPS}(B=1)$$

结果就是：做更多 FLOPs，反而让 GPU 运行得更高效。throughput（samples/s）随 batch 增加的速度远快于 latency 的增长。

这个现象非常重要，因为它清晰展示了 FLOPs 增加并不意味着 latency 同比例增加。

MoE：routing 改变 GEMM shape
#

MoE 是一个特别好的例子，展示 “same FLOPs ≠ same latency”。

假设 batch = 128 tokens，top-k = 1。routing 决定每个 token 去哪个 expert。

Routing A：集中

1Expert 0: 64 tokens  →  GEMM: [64, D] × [D, H]
2Expert 1: 64 tokens  →  GEMM: [64, D] × [D, H]

Routing B：分散

1Expert 0: 2 tokens   →  GEMM: [2, D] × [D, H]
2Expert 1: 3 tokens   →  GEMM: [3, D] × [D, H]
3Expert 2: 1 token    →  GEMM: [1, D] × [D, H]
4...
5Expert 63: 4 tokens  →  GEMM: [4, D] × [D, H]

理论上，所有 token 最终都经过一次 expert MLP。总 FLOPs 非常接近。

但实际 latency 可能差很多。

原因就在于 expert batch distribution 改变了 GEMM shape，进而改变了 Achieved FLOPS。Routing B 产生大量 skinny GEMM，效率远低于 Routing A 的两个 large GEMM。

而且还有额外的开销：dispatch、gather/scatter、routing computation、synchronization、load imbalance——这些在 FLOPs 统计里完全不存在。

关于 MoE 的结构分析，可以参考我之前写的 MoE 结构学习笔记。

GNN：进入 FLOPs 更不可靠的区域
#

GNN 用来进一步说明：有些 workload 连"主要工作是 dense compute"这个前提都不成立。

一个简单的 GNN layer 可以分成两部分：

Feature Transformation
#

$$H' = HW$$

这就是标准 GEMM，FLOPs = \(2N D_{\text{in}} D_{\text{out}}\)。这部分 FLOPs 对 latency 的解释能力和 MLP 类似。

Message Passing / Aggregation
#

1dst[edge_dst] += src[edge_src]

理论上每个 feature 可能就一个 add，FLOPs 极少。

但 GPU 实际需要做的事情远不止一个 add：

  • load edge index
  • load source feature
  • locate destination
  • read/write destination（可能需要 atomic operation）
  • perform reduction

搬运的 bytes 相对于 FLOPs 非常大，Arithmetic Intensity 极低。

而且这些 memory access 往往是 irregular 的：edge 的源和目标节点不连续，cache locality 很差，degree distribution 不均匀导致 load imbalance，atomic contention 也可能很严重。

结果就是：一个 GNN aggregation kernel 的 FLOPs 可能看起来很少，但 latency 一点也不低。

递进小结
#

MLP → MoE → GNN 形成了一条很清晰的递进：

WorkloadFLOPs 对 latency 的解释能力主要原因
Large dense MLP较强GEMM efficiency 稳定
Small-batch MLP中等skinny GEMM 效率下降
MoE更弱expert batch distribution 改变 GEMM shape
GNN GEMM 部分较强仍是标准 GEMM
GNN aggregation很弱memory-bound + irregular access

从左到右，workload 离"大的、规整的 dense GEMM"越远，FLOPs 对 latency 的预测能力就越弱。

Training vs Inference
#

文章 focus 推理，但训练和推理的 FLOPs 关系也值得简单讨论。

对一个 Linear layer \(Y = XW\)：

  • Forward： \(F_{\text{forward}} = 2BKN\)
  • Backward（计算 dX）： \(dX = dY \cdot W^T\)，需要 \(2BKN\)
  • Backward（计算 dW）： \(dW = X^T \cdot dY\)，需要 \(2BKN\)

因此：

$$F_{\text{backward}} \approx 4BKN$$$$F_{\text{forward}} + F_{\text{backward}} \approx 6BKN \approx 3 \times F_{\text{forward}}$$

CS336 里用的是 Kaplan/Hoffmann 的 convention：backward ≈ 2x forward FLOPs，总共 ≈ 3x forward。这个比例对 GEMM-heavy dense network 是比较好的粗估。

但需要注意的是：3x 不是 universal law。nonlinear operators、normalization、sparse operations、MoE routing、GNN aggregation、communication、optimizer step 都会改变这个比例。

更重要的是：训练和推理的 Achieved FLOPS 也可能完全不同。

训练时 batch size 通常较大，GEMM shape healthy，GPU 可以被充分利用。

而 online inference 为了低 latency，batch 经常是 1 / 2 / 4，导致 skinny GEMM，GPU utilization 可能远低于训练时。

于是出现一个反直觉的情况：inference 每个 sample 做的 FLOPs 明明比 training 少很多，但 GPU utilization 也低很多。不能只比较 theoretical FLOPs，还要考虑 achieved efficiency 的差异。

MFU
#

CS336 的 adamw_accounting 作业里引入了 MFU（Model FLOPs Utilization）：

$$\text{MFU} = \frac{\text{Achieved FLOPS}}{\text{Peak FLOPS}}$$

它回答：当前 workload 实际利用了 GPU 理论计算能力的多少。

比如 GPU peak BF16 = 100 TFLOPS，模型 FLOPs = 10 GFLOPs，latency = 0.5 ms：

$$\text{Achieved FLOPS} = \frac{10G}{0.0005} = 20\ \text{TFLOPS}$$$$\text{MFU} = \frac{20}{100} = 20\%$$

这个例子把 FLOPs、Peak FLOPS、Achieved FLOPS、Latency 几个概念串了起来。

但有一个容易掉进去的坑：如果 workload 是严重 memory-bound 的，低 MFU 并不代表实现一定差。

回想 Roofline——如果 workload 的 AI 远低于 ridge point，那它根本就不可能接近 compute peak。这时候低 MFU 是 Roofline 决定的，不是 kernel 写得烂。

不要把 MFU 当成唯一的优化目标。

回到模型调度
#

回到最开始的问题：用 FLOPs 给模型做调度。

如果 scheduler 给每个模型一个 profile：

1ModelProfile {
2    flops
3}

然后认为 Model A = 10 GFLOPs、Model B = 20 GFLOPs，于是 B 大约需要 A 两倍 GPU 时间。

这个假设只有在 hardware 相同、dtype 相同、workload structure 相近、GEMM shape 相近、Arithmetic Intensity 相近、achieved efficiency 相近时才比较合理。

否则 \(\text{FLOPs}_A / \text{FLOPs}_B\) 不能直接推出 \(\text{Latency}_A / \text{Latency}_B\)。

Scheduler Performance Model 应该怎么演进
#

Level 0：

1ModelProfile { flops }

只能做非常粗的估计。

Level 1：

1ModelProfile { flops, operator_types, gemm_shapes }

开始知道 FLOPs 是由什么 shape 的计算组成的。

Level 2：

1ModelProfile { flops, gemm_shapes, arithmetic_intensity }

可以用 Roofline 做 first-order hardware estimation。

Level 3：

1ModelProfile {
2    theoretical_flops,
3    workload_shape,
4    measured_latency[hardware],
5    achieved_flops[hardware],
6}

也就是 offline profiling。这是最终最可靠的方案。

结论
#

全文最核心的认知是这个公式：

$$\text{Latency} = \frac{\text{FLOPs}}{\text{Achieved FLOPS}} = \frac{\text{Work}}{\text{Efficiency}}$$

FLOPs 描述 Work。Achieved FLOPS 描述 Efficiency。Latency 才是 Performance。

不要把关系简化成 FLOPs → Latency。中间还隔着 Hardware Efficiency 这一层。

具体来说：

  • FLOPs 告诉我们要完成多少数学工作
  • Arithmetic Intensity + Roofline 告诉我们这些工作更可能受 compute 还是 memory 限制
  • GEMM shape / parallelism 告诉我们即使资源上限允许，GPU 能否真正获得高 utilization
  • Profiling 最终告诉我们在具体 GPU、具体 kernel、具体 input shape 下，实际到底需要多久

理论模型用来解释性能，真实 profiling 用来预测性能。

Theory explains. Profiling predicts.

对于模型调度这类问题，FLOPs 适合做第一阶估计和 workload 描述。但真正要做 latency-aware scheduling，最终应该依赖 workload-aware profiling，而不是简单按 FLOPs 分配 GPU。
