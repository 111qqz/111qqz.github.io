Tensor Parallelism：为什么矩阵乘法可以拆分到多张 GPU 上？

2026-10-23·5451 字·11 分钟
Deep-Learning Distributed-Training Tensor-Parallelism Ml-Infra 6.S191
👁️ 次阅读

起因
#

上一篇写完 ZeRO 之后，我对 Data Parallelism 这条线有了比较完整的理解：DDP 让每张 GPU 各算各的梯度再同步，ZeRO 在此基础上把 Model States 的冗余存储一层一层消除。但有一件事一直让我觉得没想通——ZeRO-3 虽然把参数、梯度和 Optimizer States 分片存储了，每张 GPU 的 forward 和 backward 计算量并没有减少。7B 模型 4 卡 ZeRO-3，单卡 Model States 降到约 28 GB，但做 forward 时仍然要 AllGather 完整参数、用完整权重算完整输出。

继续看 MIT 6.S191 Lecture 9 讲 Tensor Parallelism 的部分，了解到 TP 解决的是另一个问题：把单个算子的计算本身拆到多张 GPU 上执行。每张 GPU 只负责权重矩阵的一个分片，局部输出合起来，数学上等价于单卡的完整结果。

我能理解"拆分计算"这个目标，但一开始有几个问题想不清楚：

  • 一个矩阵乘法为什么能拆成多份分别算，最后还能拼回正确结果？
  • 了解到有 Column Parallel 和 Row Parallel 两种拆分方式以后，又有一个疑问：为什么需要两种？只用一种不行吗？
  • 后来发现 Megatron-LM 把两种方式组合使用，说可以省掉中间通信——这又是怎么做到的？

这篇按顺序把这几个问题想清楚。

一个矩阵乘法，先算完整结果
#

全文使用同一个数值例子。一个最简单的 Linear Layer（不带 bias）：

$$ Y = XW $$

其中：

$$ X = [1, 2] \quad \text{shape: } (1, 2) $$$$ W = \begin{bmatrix} 1 & 2 & 3 & 4 \\ 5 & 6 & 7 & 8 \end{bmatrix} \quad \text{shape: } (2, 4) $$

手算一下完整输出：

$$ Y = [1 \times 1 + 2 \times 5,\ 1 \times 2 + 2 \times 6,\ 1 \times 3 + 2 \times 7,\ 1 \times 4 + 2 \times 8] = [11, 14, 17, 20] $$

shape 是 \((1, 4)\)。

这就是单卡计算的完整结果。现在的问题是：如果有两张 GPU，能不能让每张卡只算一部分，最后恢复出同样的 \([11, 14, 17, 20]\)？

应该怎么划分权重矩阵 \(W\)？

按列拆——每张 GPU 负责不同的输出列
#

最直接的想法是把 \(W\) 按列切开。

\(W\) 有 4 列，分成两半：

$$ W_0 = \begin{bmatrix} 1 & 2 \\ 5 & 6 \end{bmatrix}, \quad W_1 = \begin{bmatrix} 3 & 4 \\ 7 & 8 \end{bmatrix} $$

也就是 \(W = [W_0 \mid W_1]\)。

两张 GPU 都持有完整的输入 \(X = [1, 2]\)，分别计算：

GPU 0：

$$ Y_0 = XW_0 = [1 \times 1 + 2 \times 5,\ 1 \times 2 + 2 \times 6] = [11, 14] $$

GPU 1：

$$ Y_1 = XW_1 = [1 \times 3 + 2 \times 7,\ 1 \times 4 + 2 \times 8] = [17, 20] $$

最终把两个结果拼接起来：

$$ Y = [Y_0 \mid Y_1] = [11, 14, 17, 20] $$

和单卡结果完全一致。

这里有一个地方让我停下来想了一下：为什么结果是拼接而不是求和？

回头看公式就能想通——GPU 0 算的是前两列对应的输出元素，GPU 1 算的是后两列对应的输出元素。不同 GPU 负责的是不同的输出位置，彼此之间没有重叠。所以合并时只需要按位置拼在一起，不涉及任何加法。

写成一般形式：

$$ X [W_0 \mid W_1] = [XW_0 \mid XW_1] $$

这就是 Column Parallel 的数学基础。矩阵乘法对列维度的线性性，让按列拆分后的结果可以直接拼接还原。

按行拆——为什么这次必须求和
#

换一种拆法。还是同样的 \(X\) 和 \(W\)，但这次按 \(W\) 的行切开。

\(W\) 有 2 行，每张 GPU 拿一行：

$$ W_0 = [1, 2, 3, 4] \quad \text{shape: } (1, 4) $$$$ W_1 = [5, 6, 7, 8] \quad \text{shape: } (1, 4) $$

既然 \(W\) 的行被拆了，输入 \(X\) 也要沿对应维度拆分：

$$ X_0 = [1], \quad X_1 = [2] $$

两张 GPU 分别计算：

GPU 0：

$$ Y_0 = X_0 W_0 = 1 \times [1, 2, 3, 4] = [1, 2, 3, 4] $$

GPU 1：

$$ Y_1 = X_1 W_1 = 2 \times [5, 6, 7, 8] = [10, 12, 14, 16] $$

这时候如果直接拼接 \(Y_0\) 和 \(Y_1\)，会得到长度为 8 的向量——shape 变了，数值也对不上。

正确的做法是逐元素求和：

$$ Y = Y_0 + Y_1 = [1+10,\ 2+12,\ 3+14,\ 4+16] = [11, 14, 17, 20] $$

又拿到了正确结果。

但为什么这次变成了求和？

从某一个输出元素入手就能看清楚。完整计算中，\(Y\) 的第一个元素是：

$$ Y[0] = 1 \times 1 + 2 \times 5 = 11 $$

两张 GPU 分别贡献了：

  • GPU 0 算出了 \(1 \times 1 = 1\)（第一个加数）
  • GPU 1 算出了 \(2 \times 5 = 10\)（第二个加数）

它们算的是同一个输出元素的不同部分和。要得到完整值，必须把各自的贡献加起来。

一般形式：

$$ [X_0 \mid X_1] \begin{bmatrix} W_0 \\ W_1 \end{bmatrix} = X_0 W_0 + X_1 W_1 $$

Column Parallel 拆的是输出维度（每张 GPU 算不同的输出列），所以合并是拼接。Row Parallel 拆的是内积的求和维度（每张 GPU 算同一个输出元素的部分贡献），所以合并是求和。 这个区别不是人为选择的，而是矩阵乘法的数学结构决定的。

推广到多 GPU：Shape 与通信方式
#

前面用 2 GPU 和小矩阵把原理看清楚了。推广到真实规模：

$$ X: (32, 1024), \quad W: (1024, 4096), \quad P = 4\ \text{（GPU 数量）} $$

Column Parallel：

项目Shape
每卡权重 \(W_i\)\((1024, 1024)\)
每卡输出 \(Y_i\)\((32, 1024)\)
完整输出 \(Y\)\((32, 4096)\)

4 张 GPU 各算出 \(\frac{1}{4}\) 的输出列。如果后续算子需要完整的 \(Y\)，可以执行 AllGather——通信原语那篇已经介绍过：每张 GPU 把自己的分片广播给所有人，最终每张 GPU 都持有完整数据。

Row Parallel：

项目Shape
每卡输入 \(X_i\)\((32, 256)\)
每卡权重 \(W_i\)\((256, 4096)\)
每卡局部输出 \(Y_i\)\((32, 4096)\)
完整输出 \(Y\)\((32, 4096)\)

4 张 GPU 各算出完整 shape 的局部贡献，但数值只是部分和。要拿到最终结果，需要 AllReduce(SUM)。

需要注意：数学上的 Concatenate / Sum 和分布式通信中的 AllGather / AllReduce 不是同一件事。 前者描述的是如何从局部结果恢复完整输出，后者是多 GPU 之间实际执行数据交换的通信模式。数学上需要合并结果，不代表每种实现都必须立即通信——具体什么时候通信、能不能延迟或省略，取决于下一个算子需要什么样的数据布局。

对照一下两种方式：

Column ParallelRow Parallel
权重拆分方式按列：\(W_i\) 是 \(W\) 的第 \(i\) 组列按行：\(W_i\) 是 \(W\) 的第 \(i\) 组行
输入要求每卡持有完整 \(X\)输入也需拆分：\(X_i\) 是 \(X\) 对应的列分片
局部输出含义完整输出的一个列分片完整输出的部分和
合并方式（数学）拼接（Concatenate）求和（Sum）
典型通信原语AllGatherAllReduce(SUM)

两层连续 Linear——中间的通信能不能省？
#

真实模型中，矩阵乘法不会只出现一次。考虑连续两个 Linear Layer：

$$ H = XW_1, \quad Y = HW_2 $$

shape：

$$ X: (B, N), \quad W_1: (N, M), \quad W_2: (M, K) $$

假设用 \(P\) 张 GPU，且 \(M\) 可以整除 \(P\)。

最直接的做法是两层都用 Column Parallel。但这样有一个问题：

  • 第一层 Column Parallel 输出：每张 GPU 持有 \(H_i: (B, M/P)\)——输出被按列分了片
  • 第二层 Column Parallel 输入：需要完整的 \(H: (B, M)\) 来和自己的 \(W_{2,i}\) 相乘

中间必须执行一次 AllGather 把 \(H\) 的分片拼回完整矩阵。

后来看 Megatron-LM 的设计，发现它的做法不同：第一层用 Column Parallel，第二层用 Row Parallel。

第一层 Column Parallel：

$$ H_i = XW_{1,i}, \quad H_i: (B, M/P) $$

每张 GPU 拿到的 \(H_i\) 是 \(H\) 的一个列分片。

第二层 Row Parallel。Row Parallel 的输入本来就需要是分片的——每张 GPU 拿输入的一个片段和对应的权重子矩阵相乘：

$$ Y_i = H_i W_{2,i}, \quad W_{2,i}: (M/P, K) $$

最终：

$$ Y = \sum_i Y_i = \sum_i H_i W_{2,i} $$

用一次 AllReduce(SUM) 就能拿到完整结果。中间不需要 AllGather。

写到这里我回过头想了一个问题：第一层 Column Parallel 的输出分片，恰好可以作为第二层 Row Parallel 的输入分片，这到底是巧合还是必然？

想了一会儿，发现这不是巧合。

两个连续矩阵乘法本身就共享中间维度 \(M\)——第一层的输出维度是 \(M\)，第二层的输入维度也是 \(M\)。Column Parallel 沿 \(M\) 拆分输出列，Row Parallel 沿 \(M\) 拆分输入行。只要两层对 \(M\) 维度采用一致的分片规则（比如都是均匀地分成 \(P\) 份，第 \(i\) 张 GPU 拿第 \(i\) 个分片），局部数据就能直接衔接。

但必须强调"一致"这个条件。\(H_i\) 是 \(H\) 的第 \(i\) 个列分片，\(W_{2,i}\) 是 \(W_2\) 的第 \(i\) 个行分片——它们必须严格一一对应。GPU 0 的 \(H_0\) 必须和 \(W_{2,0}\) 配对，不能随意交换分片顺序。

维度匹配来自矩阵乘法的数学结构；分片数据范围的一一对应，则来自 TP 对数据布局的主动设计。

关于收益和边界，几点值得记住：

  • 省掉了一次中间 AllGather 通信。
  • 不需要在中间物化完整的 \(H\) 矩阵，每张 GPU 上的峰值 activation 更小。
  • 最后仍然需要一次 AllReduce(SUM) 来聚合部分和。
  • 并行并非无成本：GPU 间通信、局部 GEMM 规模变小带来的算力利用率变化、通信和计算能否重叠，都会影响实际加速比。4 张 GPU 不等于 4 倍加速。

两层之间有 GELU，还能直接连接吗
#

真实 Transformer 的 FFN 不是裸的两层 Linear。典型形式是：

$$ Y = \operatorname{GELU}(XW_{\text{up}}) W_{\text{down}} $$

两个矩阵乘法之间夹了一个 GELU。Column + Row 的组合还能用吗？

可以。因为 GELU 是逐元素计算的——每个输出元素只依赖对应位置的输入，不依赖其他位置的值。

第一层 Column Parallel 的输出是按列分片的 \([H_0 \mid H_1]\)。对它执行 GELU：

$$ \operatorname{GELU}([H_0 \mid H_1]) = [\operatorname{GELU}(H_0) \mid \operatorname{GELU}(H_1)] $$

每张 GPU 独立对自己的分片执行 GELU，不需要看到其他 GPU 的数据。执行完之后，数据仍然是按列分片的，直接交给第二层的 Row Parallel。

ReLU 同理。逐元素算子不会引入跨分片的数据依赖，因此不会破坏 Column + Row 之间的直连。

一个反例：LayerNorm 为什么不能对分片独立执行
#

是不是所有算子都可以对分片独立执行？

考虑 LayerNorm。假设某一层的隐藏向量是：

$$ H = [1, 3, 5, 7] $$

分配在两张 GPU 上：GPU 0 持有 \([1, 3]\)，GPU 1 持有 \([5, 7]\)。

LayerNorm 需要沿全部 4 个特征计算均值：

$$ \mu = \frac{1 + 3 + 5 + 7}{4} = 4 $$

但如果各 GPU 只用本地数据算均值，GPU 0 得到 \(\frac{1+3}{2} = 2\)，GPU 1 得到 \(\frac{5+7}{2} = 6\)。两个都不等于全局均值 4。

方差同理。LayerNorm 不是逐元素算子，它的每个输出元素依赖同一归一化维度上的所有输入。分片后存在跨 GPU 的数据依赖。

但这不意味着必须先 AllGather 完整的 \(H\) 再做 LayerNorm。

我想到一个类比：假设全年级有 1000 名学生，分成 20 个班，每班 50 人。要算全年级平均分，并不需要收集每个学生的成绩——只需要每个班主任报告本班的总分，把 20 个总分加起来除以 1000 就行了。

对均值来说：

$$ \mu = \frac{\sum_{\text{all}} x_j}{N} = \frac{\sum_{\text{GPU}} \text{local\_sum}}{N} $$

各 GPU 局部计算 \(\text{sum}(x)\)，通过一次 AllReduce(SUM) 聚合局部和，再除以 \(N\) 就是全局均值。

对方差来说，还需要一个二阶统计量。利用：

$$ \operatorname{Var}(X) = E[X^2] - (E[X])^2 $$

各 GPU 可以局部计算 \(\text{sum}(x)\) 和 \(\text{sum}(x^2)\)，通过 AllReduce 聚合这两个标量统计量，就能算出全局方差。通信量只是两个标量的 AllReduce，远小于整个 \(H\) 向量的 AllGather。

几点补充：

  • 实际数值实现中应关注浮点稳定性。\(E[X^2] - (E[X])^2\) 在数值上可能有精度问题，工程上可能采用更稳定的分布式方差算法（如 Welford 算法的分布式版本）。
  • LayerNorm 通常沿指定的特征维度计算，而不是对整个 batch 的所有元素统一归一化。如果归一化涉及的维度完全在本地 GPU 上（比如每张 GPU 持有完整的 hidden dim，分片发生在 batch 或 sequence 维度），则不需要跨 GPU 通信。
  • 这个例子是为了说明分片布局与数据依赖的关系，不代表标准 Transformer TP 在 Column Parallel 与 Row Parallel 中间一定会插入需要跨 GPU 通信的 LayerNorm。在 Megatron-LM 的典型设计中，LayerNorm 在 MLP 和 Attention Block 的入口执行，每张 GPU 对自己持有的完整 hidden state 局部计算，不涉及 TP 维度的通信。

算子是否需要跨 GPU 通信，取决于它的数据依赖关系和数据在 GPU 之间的分布方式，而不只是算子的类型。

Transformer 中的实际应用
#

把前面的数学映射到 Transformer 的两个核心模块。

MLP
#

Transformer 的 FFN 典型结构：

$$ Y = \operatorname{GELU}(X W_{\text{up}}) W_{\text{down}} $$

按照前面的分析：

  • \(W_{\text{up}}\)：Column Parallel，每张 GPU 持有 \((d, d_{\text{ff}}/P)\) 的分片
  • GELU：各 GPU 本地独立执行
  • \(W_{\text{down}}\)：Row Parallel，每张 GPU 持有 \((d_{\text{ff}}/P, d)\) 的分片
  • 最后一次 AllReduce(SUM) 聚合结果

整个 MLP 只需要一次跨 GPU 通信。

Multi-Head Attention
#

Multi-Head Attention 的结构天然适合 TP。

假设模型有 8 个 Attention Heads，用 4 张 GPU。每张 GPU 负责 2 个 Heads。

每个 Head 的 QKV Projection 和 Attention 计算是独立的——Head 0 不需要 Head 3 的数据来算自己的注意力输出。各 GPU 对自己负责的 Heads 独立计算 QKV、Attention Score、Softmax 和加权求和，最后通过 Output Projection 的 Row Parallel 聚合所有 Heads 的结果。

和 MLP 类似，整个 Attention Block 也只需要一次 AllReduce。

这里不展开 GQA、MQA、KV Cache 或 Sequence Parallelism——这些是正交的优化维度，不影响 TP 的基本原理。

TP 与 ZeRO/FSDP 的区别
#

ZeRO 那篇讨论的是 Model States 的分片存储。ZeRO-3 把参数、梯度和 Optimizer States 都分散到多张 GPU 上，但计算时会通过 AllGather 临时收集完整参数，每张 GPU 仍然执行完整的 forward 和 backward。

TP 做的事情不同：每张 GPU 始终只持有权重的一个分片，计算的也只是输出的一部分，不需要在计算前收集完整参数。

参数被分片存储，并不意味着计算也被分片执行。ZeRO 分片的是存储，TP 分片的是计算。

这不意味着 TP 一定更优。两者解决的问题和付出的代价不同：

  • ZeRO 的通信是 AllGather 参数和 ReduceScatter 梯度，通信量可预测，且在大 batch 下可以和计算重叠。
  • TP 的通信在每个算子内部发生（AllReduce），粒度更细、延迟更敏感。如果 GPU 间的互连带宽不够高（比如跨节点的网络），TP 的收益会被通信延迟吃掉。

实际系统中通常组合使用：节点内的高带宽互连（如 NVLink）跑 TP，节点间的较低带宽互连跑 ZeRO/FSDP 或 Pipeline Parallelism。

写在最后
#

从一个 \(1 \times 2\) 乘 \(2 \times 4\) 的小例子开始，到 Transformer MLP 和 Multi-Head Attention 的 TP 设计，核心思路其实就是在反复利用矩阵乘法的数学性质。

三个让我觉得值得记住的认识：

TP 的可行性首先建立在矩阵乘法的数学可分解性上。 按列拆可以独立算不同的输出列（拼接），按行拆可以独立算同一个输出的部分和（求和）。这不是工程上的 hack，而是线性代数的基本性质。

Column + Row 组合能省掉中间通信，不是 Shape 恰好对上了的巧合，而是对共享中间维度采用一致分片策略的结果。 连续两层矩阵乘法天然共享中间维度 \(M\)，只要两层在 \(M\) 上用相同的分片规则，第一层的输出分片就直接是第二层的输入分片。

是否需要通信，取决于算子的数据依赖和分片布局，而不只是算子的类型。 逐元素算子（GELU、ReLU）不引入跨分片依赖，可以直接在分片上独立执行。需要全局统计的算子（LayerNorm）则必须聚合信息——但未必需要收集完整数据，聚合统计量往往就够了。

好的 Tensor Parallelism 设计，不只是让每张 GPU 算得更少，而是让它们尽可能少地为交换数据而等待。
