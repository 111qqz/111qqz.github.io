开公司 VPN 后 ChatGPT 无法访问：一场 DNS 归属与透明代理的冲突

起因
#

最近在家办公时，遇到一个不大不小的网络冲突。为了访问公司内网的服务，我需要在 Windows 11 笔记本上连着公司的 VPN 客户端（UniVPN，基于联软）。但每次一连上这个 VPN，浏览器里的 chatgpt.com 就直接罢工了，表现为拒绝访问或无法加载。

这是一个看起来非常像「VPN 把网络搞坏了」的常见现象。遇到这种情况，多数人的本能反应大概是在查公网资料和访问内网之间反复开关 VPN。但这种妥协对工程师来说实在有些难受，特别是当你的工作流需要频繁在这两者之间切换时，这种断裂感是无法忍受的。直觉告诉我，这不太可能是网络在物理层面断了，更像是某种路由表抢占或 DNS 策略的冲突。于是我决定把这个黑盒稍微打开看看，彻底把这个问题解决掉。

现象
#

具体症状非常确切，可以通过复现来明确边界： 打开 UniVPN 后，访问 chatgpt.com 会显示一个典型的防护拦截页面，原文大意是：“Unable to load site / Please try again later. If you are using a VPN, try turning it off…"。在这个错误页面下方，清晰地标着一行环境指纹：[IP: <一台香港 VPS 的 IP> | Ray ID: ...]。这台香港 VPS 正是我自己搭的代理节点。 只要关掉 UniVPN，刷新页面，ChatGPT 的加载就会瞬间恢复正常。

这里有一个容易把排查思路带偏的观察：在开着 UniVPN 的情况下，页面报错显示我的出口 IP 是那台香港 VPS。而事实上，香港机房的 IP 对于 ChatGPT 来说本就是非法的（会被严格风控和封锁）。正因如此，我之前专门在路由器的透明代理上配置了分流规则——让 chatgpt.com 等 AI 相关的域名走专门的解锁链路，绝对不要走香港节点。 但现在一打开 UniVPN，这些 AI 域名居然又开始走香港节点了。这说明：连上 VPN 后，路由器上的域名分流规则彻底失效了，流量「漏」到了默认的错误节点上。

排查
#

既然外网是通的（只是掉到了错误的节点上），且断开公司 VPN 就能恢复，我们可以先排除一些基础层的故障：TLS 握手正常、TCP 连通性没问题、UniVPN 隧道本身运行良好，而且公司侧的内网 DNS 对内网域名的解析也没有任何报错。

既然上层没问题，那就得往下走，看操作系统的网络接口是怎么配置的。 我用 PowerShell 检查了当前所有网卡的优先级（metric）以及各自绑定的 DNS 状态：

1Get-NetIPInterface -AddressFamily IPv4 | Select-Object InterfaceAlias, InterfaceMetric
2Get-DnsClientServerAddress -AddressFamily IPv4 | Select-Object InterfaceAlias, ServerAddresses

输出的要点十分清晰，矛头直指网卡优先级：

  • UniVPN 成功连接后，在系统中创建了一个 TAP 网卡（本地连接），它的 IPv4 metric 值被强势地设为了 1，绑定的 DNS 服务器是 <公司DNS>。
  • 相比之下，我家里 WLAN 接口的 metric 值是 35，绑定的 DNS 是路由器的网关地址 192.168.2.1。

在操作系统的网络协议栈中，metric（度量值）决定了多条网络路径存在时系统默认选择哪一条。metric 值越小，优先级越高。多数企业级 VPN 客户端为了所谓的合规管控，往往具有极强的侵入性：它们不仅要接管流量，还要强制接管系统的解析权。UniVPN 将自身 TAP 网卡的 metric 压到了 1，粗暴地霸占了最高优先级。这意味着 Windows 会默认把所有的 DNS 查询，不管是不是内网域名，统统发往优先级最高的公司 DNS。

9 月 10 日 18:24 左右，我发现了这个 metric 被抢占的现象，当时我尝试了最直接的暴力修复：通过系统配置把 TAP 网卡的 metric 改成 100，让它低于家里 WLAN 的 35，以此把网络的主导权还给家里路由器。然而失败了——UniVPN 有一个后台守护进程在死盯网卡配置，刚改完几秒钟，它就又把 metric 强行刷回了 1。 18:36 时，我甚至写了个脚本挂在 Windows 计划任务里，每 3 分钟强行恢复一次 metric。但这种猫鼠游戏显然不是长久之计，只会让网络状态处于频繁的抖动中。我很快意识到，对抗企业 VPN 客户端的写死逻辑是没有意义的，必须寻找更上层的机制。

根因
#

为什么 DNS 被发往公司，会导致透明代理的域名分流失效？这就必须回过头来，审视一下我家庭网络底层的代理架构。

我家的网关是 192.168.2.1，在这台路由器背后，跑着一个配置完善的透明代理。为了实现无感的域名分流，透明代理采用的是基于 fake-ip（伪造 IP）的机制，使用的网段是 198.18.0.0/16。 为了把事情说清楚，我们需要对比一下有无 VPN 两种状态下的数据包走向。

在正常情况下（不开公司 VPN）：

  1. 笔记本请求解析 chatgpt.com，DNS 请求正常发给家里的路由器。
  2. 路由器上的透明代理截获这个请求，并不去真正查询它的公网 IP，而是直接从保留网段拿一个假 IP（比如 198.18.0.28）返回给笔记本。
  3. 笔记本随后向这个假 IP 发起 TCP 连接。
  4. 透明代理收到目标为 198.18.0.28 的报文后，反查其内部的映射表，知道这股流量原本是去往 chatgpt.com 的。根据我配置的 AI 域名分流规则，路由器会将这股流量发往专门的解锁节点，顺利访问。

在开启 UniVPN 的异常情况下：

  1. TAP 网卡的 metric 变成了 1。笔记本不再向路由器发起 DNS 查询，而是越过路由器，直接把 chatgpt.com 的解析请求发给了 <公司DNS>。
  2. 公司 DNS 老老实实地去公网上查，查到了 chatgpt.com 真实的公网 IP（比如 104.18.x.x 系列），并将其返回给笔记本。
  3. 接着，笔记本直接向这个真实的公网 IP 发起 TCP 连接。
  4. 由于这是一条发往真实公网 IP 的连接，它没有命中 fake-ip 的专属网段，完美绕过了透明代理基于域名的精细分流逻辑。
  5. 路由器底层收到这股未知的 TCP 流量，无法识别出它其实是去往 chatgpt.com 的，于是只能按照底层的 fallback 逻辑，将其扔进默认的全局出海路由——而我的默认出海节点，正是那台香港 VPS。
  6. 结果，去往 ChatGPT 的流量阴差阳错地从被 OpenAI 封锁的香港节点出去了，从而触发了 WAF 的阻断拦截。

虽然透明代理运行在路由器底层，其包级别的流控机制非常复杂，我也没有在客户端侧 100% 抓包确认内核层面的所有走向；但有一个核心逻辑是反复复现过的：只要通过手段让 DNS 请求回到路由器，问题立刻恢复。

这是一个非常深刻的网络机制冲突：在基于 fake-ip 的透明代理网络中，DNS 的归属决定了流量的分流走向；一旦 VPN 的高优先级网卡抢占了 DNS 的解析权，原本依赖特定 DNS 劫持的代理链路就会从源头断裂。

修复
#

既然不能在网卡 metric 上和 VPN 硬刚，那我们就必须在系统网络栈的更上层进行接管：让 Windows 强制把不同的域名交给不同的 DNS 服务器去解析，也就是实现域名级 DNS 分流。

在 Windows 环境中，解决这类问题的标准也是最优雅的方案是使用 NRPT（Name Resolution Policy Table，名称解析策略表）。NRPT 可以在完全不改变网卡优先级的前提下，在系统 DNS 解析器层面强制规定特定后缀的域名该去哪里问。

整个修复方案分两步走：首先确保内网域名正常走公司 DNS，然后利用 catch-all 规则，将其余所有外网域名的解析交还给本地路由器。 当晚 22:36，我理清了全局 DNS 与 fake-ip 的关系后，在管理员权限的 PowerShell 中执行了以下配置：

 1# 1) 将公司内网域名强制发往公司 DNS，确保内网服务不受影响
 2Add-DnsClientNrptRule -Namespace "<公司内网域名>" -NameServers "<公司DNS>" -DisplayName "UniVPN internal"
 3
 4# 2) 建立 catch-all 规则，将其余所有域名强制发往家里路由器（以此恢复 fake-ip 链路）
 5Add-DnsClientNrptRule -Namespace "." -NameServers "192.168.2.1" -DisplayName "All other DNS via router"
 6
 7# 3) 关闭「智能多网卡名字解析」，避免在多网卡场景下系统往所有 DNS 乱发请求
 8$p = "HKLM:\SOFTWARE\Policies\Microsoft\Windows NT\DNSClient"
 9New-Item -Path $p -Force | Out-Null
10New-ItemProperty -Path $p -Name DisableSmartNameResolution -PropertyType DWord -Value 1 -Force
11
12# 4) 清理 DNS 缓存，让新规则立刻生效
13ipconfig /flushdns

在这个方案里，我们通过 NRPT 定下了更高的规则维度。UniVPN 想在网卡层面当大爷就让它当，但在请求真正发出去之前，NRPT 已经按照域名完成了精准拆分。紧接着，我删除了之前尝试改 metric 的计划任务。

验证
#

在开着 UniVPN、TAP 网卡 metric 仍然顽固保持为 1 的条件下，进行实测验证。

首先确认 NRPT 规则的命中情况：

1Get-DnsClientNrptRule

输出清晰地显示了规则表：{.} 命中了 192.168.2.1；{<公司内网域名>} 命中了 <公司DNS>。

随后验证最关键的外网解析：

1Resolve-DnsName chatgpt.com

命令输出显示返回的 IP 是 198.18.0.28。这是一个非常标准的 fake-ip 地址！这说明我们对域名的查询已经成功被 NRPT 导向了家里的路由器，并且完美触发了路由器底层的透明代理劫持机制。

最后测试公司内网环境：

1Resolve-DnsName <内网主机>

输出显示返回了正确的内网 IP <内网主机IP>，一切运转如初。

回到浏览器中打开 chatgpt.com，不再有任何拦截提示，页面秒开；同时，公司内网的远程桌面等服务也能稳定连接。

这里有一个额外容易踩坑的地方需要说明：在验证是否能访问 ChatGPT 时，请务必使用浏览器直接测试。如果你习惯性地用 curl 或 PowerShell 发起探测请求去直接连接 https://chatgpt.com，会因为你缺乏正常的浏览器客户端指纹（Client Hello 等特征），直接被 Cloudflare 的防火墙阻断并返回 403 错误。这跟你的透明代理没关系，纯粹是触发了业务风控，不能拿这种方法来判断底层网络通不通。

注意事项
#

使用 NRPT 虽然优雅彻底，但它不是一劳永逸的，有几个局限和维护要点需要心里有数。

第一，我们在 catch-all 规则中将外网 DNS 硬编码死在了 192.168.2.1 这个网关上。如果明天你带着这台笔记本去了公司或者咖啡厅，连接了新的网络环境，这条强制指定的 DNS 可能会导致你无法解析任何外网域名（因为别的地方网关不一定是这个 IP，或者没有配置透明代理）。当换网络发现无法上网时，需要先删掉这条全局规则：

1Get-DnsClientNrptRule | Where-Object { ($_.Namespace -join ",") -eq "." } | Remove-DnsClientNrptRule -Force

第二，如果公司的基础设施团队日后变更了 DNS 地址，你需要同步更新 <公司内网域名> 的 NRPT 规则，否则内网解析会失效。

第三，也是最容易误解的一点：NRPT 的本质只是决定了「系统把 DNS 报文发给谁去问」。它本身不改变操作系统的路由表，更不会改变实际流量的物理走向。它解决的仅仅是 DNS 归属问题，进而间接地修复了依赖 DNS 劫持的透明代理机制。

结论
#

整个排查和修复过程到此终于收口。回头复盘，这是一个初看起来极其像「VPN 把网络彻底阻断」的表象问题，但在抽丝剥茧之后，最终收敛到了「DNS 的归属决定了流量走向」这件网络底层的小事上。

在排查这类涉及 VPN、透明代理、家庭网关的复杂网络冲突时，我们很容易被底层的路由表、错综复杂的网络日志甚至外部的反爬机制吸引全部注意力。但经验表明，当你发现直连和代理的行为在同一台设备上发生诡异冲突时，先去查当前域名到底是由谁在解析，往往是最具性价比的排查手段。

永远不要去和那些写死了逻辑的企业 VPN 客户端抢网卡的优先级，在操作系统的网络栈中，通过合理的策略（如 NRPT 域名级分流）来实现分层控制，才是解决复杂问题的体面方式。
